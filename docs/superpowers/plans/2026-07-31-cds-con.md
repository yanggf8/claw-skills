# cds-con — credit-spread monitor, built Rust-first

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Deliver the credit-spread picture daily, and keep its data fresh. `price cds fetch/show` already exists — data layer and read command, 8 FRED series — but the *con* half was never built: no skill, no schedule, no delivery. Measured cost: on 2026-07-31 the daily series' newest row was 2026-07-24, seven days stale, because nothing runs the fetch.

**Tech Stack:** Rust 2021, a new shared `credit-store` crate in `../../b/gwebcdb`, `turso-util`, `claw-core`.

## This is NOT a port, and that changes everything

Every skill in this repo arrived by porting a working Python original, which meant a differential against a live oracle could prove byte-equality. **cds-con has no Python original.** There is nothing to diff against, so:

- **The tests are the entire specification.** The failure mode is a plausible-looking implementation passing weak tests — the same situation as oilcon's Task 3 (the backfill policy), which was the one part of that port with no oracle.
- **Do not write a `tests/differential.rs`.** There is nothing on the other side. Saying so explicitly because all three Phase ③ crates have one and its absence here will look like an omission.
- **The one thing that *can* be checked against an oracle** is the arithmetic: `price cds show` already computes these percentiles and is covered by 274 lines of tests in `crates/price-cli/tests/credit.rs`. Task 0 must not change a single number it produces — that suite passing unchanged is the proof.

## Settled design decisions — do not relitigate

Decided by the human 2026-07-31, after reading `docs/price-cli-and-credit-data.md`:

1. **It shows the data. It does not classify.** No status ladder, no cheap-or-expensive label, no action verb — the same rule `cds show` already follows, and for the same reason: a percentile is a rank *within a stated window*, and the window can flip the conclusion. **cds-con will be the only skill here with no `狀態：` line.** That is deliberate; do not add one.
2. **The rule is not weakened by the message being pushed rather than pulled.** Asked directly whether a daily unsolicited delivery needs a verdict where a CLI query does not, the answer was that it is the same thing.
3. **Add the Baa−Aaa quality spread.** It does not exist yet — `docs/price-cli-and-credit-data.md` lists it under "Known open items" as *"the longest-history credit-stress measure available and must currently be computed by hand"*.
4. **Fetch and deliver are two separate cron jobs.** A FRED outage then affects freshness only; the message still goes out and says honestly how stale the data is. Same separation that made oilcon's preflight work.
5. **The percentile logic is extracted into a shared crate**, consumed by both `price-cli` and `cds-con` — the arrangement already proven by `market-fetch` and `price-store`.
6. **The config format gains a fourth field for the family**: `key|SERIES_ID|Label|kind`, where `kind` is `spread` or `yield`. Decided after review showed `SeriesSpec` carries only `key`/`series_id`/`label`, so a renderer splitting the two families could only do it by hardcoding key lists — which would break the standing rule that adding a series is a `price config set`, never a code edit. **Old three-field rows are already in the live DB, so the parser must accept both** and a missing `kind` is an error at *use* rather than a silent default: guessing "yield" for an unlabelled spread is exactly the false signal this split exists to prevent.
7. **The skill status reports the RUN, not the DATA — but "no usable result" is a run failure.** Staleness, a missing series and a partial refresh are reported *in the message body*, never as `degraded`: that would be a verdict about the data, contradicting decision 1, and `degraded` trips `repair_policy = retry_once`, which cannot repair stale upstream data and would deliver the identical message twice.

   An earlier revision stopped there, saying `ok` whenever the store could be read and reserving `failed` for the store being unreachable. **Review showed that conflicts with this repo's own standing rule** (`CLAUDE.md:266-267`): *"option A: the hard-failure path must not deliver. When a skill has no usable result, emit `[skill-status:failed]`"*. An empty store would have rendered every row as `n/a`, delivered it, and reported `ok` — a whole pipeline dead and the scheduler permanently green, because `skill_contract` reads markers and not the body. Narrowed:

   | Situation | Status | Deliver? |
   |---|---|---|
   | Store unreachable or the read fails | `failed` | no |
   | Readable but **zero usable observations** — empty store, or every configured series missing | `failed` | no |
   | `kind` missing so the family split cannot be rendered (decision 6) | `failed` | no |
   | Data present, however stale; or a few series missing | `ok` | yes, body says which and how old |

   "Seven days old" stays `ok`, because that is a fact about the data. "Nothing to report at all" is `failed`, because that is a fact about the run.

## The data has a trap in it, and the message must not fall into it

The eight series are **not commensurable**:

| | Series | What it is |
|---|---|---|
| **Spreads** | `baa10y`, `hy_oas`, `ig_oas` | Compensation for credit risk, risk-free rate **already removed** |
| **Yields** | `aaa`, `baa`, `hy_yield`, `ig_yield`, `ccc_yield` | Total borrowing cost, **includes** the risk-free rate |

Measured 2026-07-31, and this is why it matters:

```
baa10y     1.59   10y p10.2   stored p11.2    ← spread at a 40-year low
ccc_yield 14.28    1y p99.6   stored p93.5    ← yield at a 1-year high
hy_oas     2.79    1y p30.2   stored p18.1    ← spread low
aaa        5.52   10y p96.7                   ← yield at a 10-year high
```

These look contradictory and are not: **yields are high because rates are high, not because credit is stressed.** A message that ranks them together, or lets a reader compare a yield percentile against a spread percentile, manufactures a false signal. The two families are rendered in **separate blocks with their meaning stated**.

**Coverage is the second trap, and it does not line up with the first.** An earlier revision of this plan said "the three Moody's series reach back to 1919". **That is wrong** — and the figures contradicting it were in this session's own query output at the time it was written:

| Series | Family | Span | Frequency |
|---|---|---|---|
| `aaa`, `baa` | yield | **1919-01-01** → | monthly (n=1290) |
| `baa10y` | spread | **1986-01-02** → | daily (n=10140) |
| `hy_oas`, `ig_oas` | spread | 2023-07-28 → | daily (~3y cap) |
| `hy_yield`, `ig_yield`, `ccc_yield` | yield | 2023-07-28 → | daily (~3y cap) |

So **coverage is mixed *inside* each family**: the spread family spans 1986 and 2023; the yield family spans 1919 and 2023. A single "coverage" label per block would therefore be untrue for some of its rows. **Coverage and frequency belong on the series line, not the block header.** `docs/price-cli-and-credit-data.md` is explicit that short-coverage series must not be printed beside long-coverage ones without saying so; that constraint survives, it just cannot be discharged at block level.

Accumulating ICE history forward is precisely why the data is stored rather than re-fetched, which is also why Task 4's fetch schedule matters more than it looks.

**Every figure above is from a live `price cds show` on 2026-07-31 and was verified line by line.** An earlier revision of this block carried invented values for `ig_oas` — `0.94 / 1y p19.4 / 全庫 p12.7` against the real `0.80 / p60.0 / p22.1`. That is not a typo-grade error: p19.4 reads as *IG spreads near their one-year low*, while p60.0 is mid-range, so the fabricated line told the opposite story. It mattered more than usual because this block is the **specification the render tests are written from** — a made-up number here becomes the oracle. `hy_yield` and `ig_yield` had been left as `...`, which was at least honest about not knowing.


Fixed by this spec, each pinned by its own test:

- **Order** — spreads before yields; within a block, **longest coverage first**, so the series that can speak to history leads. Ties broken by config order, which is stable. The derived `baa−aaa` is not in `cds_series`, so "config order" cannot place it: it sorts by its coverage start like everything else, which puts it **first in the spread block** (1919, ahead of `baa10y`'s 1986). *An earlier revision stated this rule and then contradicted it in the golden below — the golden is the oracle the render tests are written from, so a rule the sample disobeys leaves the implementer guessing.*
- **Windows** — `1y`, `10y`, `全庫`. `10y` is omitted, not rendered as `insufficient-coverage`, for any series that cannot reach it; a line cluttered with refusals teaches nothing. **`insufficient-coverage` is still never silently narrowed** — the omission is visible because the coverage start is on the same line.
- **Precision** — value to 2 decimals, percentile to 1. Matches `cds show`.
- **Units** — none printed. Every series is in percent and mixing a `%` into a line that also carries `p12.7` invites misreading a percentile as a rate.
- **Provenance** — the coverage start and frequency stand in for it on each line; the FRED id is *not* printed. It is in `cds show` for a human debugging the fetch; a daily message does not need `BAMLH0A0HYM2`.
- **Freshness** — the `資料：` line states the newest date per frequency and the age in days. No threshold, no colour, no adjective: age is shown, never judged, the same rule the `observe` layer follows.
- **A missing series** renders its row as `n/a` with its coverage line intact, and the `資料：` line names it. It does not vanish, because a vanished row is indistinguishable from a series nobody configured.
- **Monthly series publish at different times, so freshness is not one number.** `baa` and `aaa` are separate FRED releases; when one lands first, the inner join that produces `baa−aaa` correctly drops the unmatched month, but the derived row is then **older than both its inputs**. The `資料：` line therefore states the **minimum** latest across monthly series, not the maximum, and the derived row carries its own latest on its own line like every other row. Taking the max would advertise a freshness the headline number does not have.

## Out of scope

- **Any verdict, ladder, or threshold.** Settled above.
- **Real CDX/iTraxx quotes.** Licensed terminal data, not obtainable; the naming rule (`source = "fred:<SERIES_ID>"`, the `series` line before any number) exists so the proxy can never be mistaken for one.
- **Backfilling ICE history beyond ~3 years.** The keyless endpoint caps it. Forward accumulation is the only route, which is what the fetch job is for.
